### 1.2 Major Dependencies

- **Strategy Versions** — `research_signals` FK to `strategy_versions`; `research_reports` reference `strategy_id` (string) and `strategy_version` (int).
- **Paper Orders** — `strategy_id` is a plain string tag without FK constraint (intentional decoupling for AMBIGUOUS correlation semantics).
- **Positions & Fills** — `paper_positions` correlate to `paper_fills` via instrument + account identity (STRONG), no direct FK.
- **Kill Switch** — Global singleton keyed by `name='global'`.
- **Risk Events** — Created by paper trading engine upon constraint violations (daily loss, position limit, capital exhaustion, kill switch).

### 1.3 Current Service Boundaries

- `app/paper_trading/engine.py` — Core order submission, risk validation, position mark-to-market.
- `app/paper_trading/routes.py` — REST endpoints for orders, positions, summary, kill switch, risk events.
- `app/monitoring/routes.py` — Health checks, metrics, strategy version registry, system status.
- `app/research/routes.py` — Research signals, evaluations, backtest reports, rankings.
- `app/historical/routes.py` — OHLCV partition browsing.

## 2. Proposed Project Entity Design

### 2.1 Minimum Durable Project Schema

```python
class Project(Base):
    __tablename__ = "projects"
    
    id: Mapped[UUID] = mapped_column(primary_key=True, default=uuid4)
    name: Mapped[str] = mapped_column(String(100), unique=True, index=True)
    slug: Mapped[str] = mapped_column(String(100), unique=True, index=True)
    description: Mapped[str | None] = mapped_column(Text, nullable=True)
    
    # Lifecycle state machine (project operational status)
    status: Mapped[ProjectStatus] = mapped_column(default=ProjectStatus.CREATED)
    # Values: CREATED, STOPPED, STARTING, RUNNING, PAUSED, STOPPING, ERROR, ARCHIVED
    
    # Execution mode (PAPER vs LIVE authorization)
    execution_mode: Mapped[ExecutionMode] = mapped_column(default=ExecutionMode.PAPER)
    # Values: PAPER, LIVE_DISABLED, LIVE_AUTHORIZED, LIVE_PAUSED
    
    # Configuration versioning
    config: Mapped[dict] = mapped_column(JSON, default=dict)
    config_version: Mapped[int] = mapped_column(integer, default=1)
    
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=utcnow)
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=utcnow, onupdate=utcnow)
```

### 2.2 Relationships

- `Project` 1:N `ProjectStrategyAssignment` (junction table binding strategies to projects with role/priority).
- `Project` 1:N `ProjectAccountAssignment` (binding paper accounts to projects; pointer to risk limits).
- `Strategy` remains independent; projects reference strategies via assignment, not ownership.

### 2.3 Concept Separation Matrix

| Concept | State Owner | State Location | UI Surface |
|---------|-------------|----------------|------------|
| A. Project lifecycle state | Project.status enum | projects table | Project card / Status panel |
| B. Strategy lifecycle state | StrategyVersion.lifecycle field | strategy_versions table | Strategy editor |
| C. Broker connectivity state | ProviderAdapter registry | Runtime memory + provider health API | Broker status panel |
| D. Execution authorization state | Project.execution_mode enum | projects table | Control panel (PAPER/LIVE badge) |
| E. PAPER/LIVE execution mode | Project.execution_mode | projects table | Execution mode banner |
| F. Kill-switch/risk state | KillSwitch singleton | kill_switches table | Risk Operations Console |

## 3. State Machine Specification

### 3.1 Project Lifecycle State Machine

```text
                ┌─────────────┐
     ┌─────────►│   CREATED   │◄────────┐
     │          └──────┬──────┘         │
     │                 │ start          │ archive
     │                 ▼                │
     │          ┌─────────────┐         │
     │          │  STARTING   │─────────┤
     │          └──────┬──────┘ success │
     │                 │                │
     │                 ▼ error          │
     │          ┌─────────────┐         │
     └──────────│    ERROR    │─────────┤
                └─────────────┘         │
                      ▲                 │
                      │                 │
                ┌─────┴─────┐     ┌─────┴─────┐
                │  RUNNING  │◄───►│   PAUSED  │
                └─────┬─────┘     └───────────┘
                      │ stop
                      ▼
                ┌───────────┐
                │ STOPPING  │
                └─────┬─────┘
                      │ success
                      ▼
                ┌───────────┐
                │  STOPPED  │
                └───────────┘
```

**Legal transitions:**
- CREATED → STARTING, ARCHIVED
- STARTING → RUNNING, ERROR
- RUNNING → PAUSED, STOPPING, ERROR
- PAUSED → RUNNING, STOPPING, ERROR
- STOPPING → STOPPED, ERROR
- STOPPED → STARTING, ARCHIVED
- ERROR → STOPPED, ARCHIVED
- ARCHIVED → (terminal, no exit)

### 3.2 Execution Authority State Machine

```text
PAPER  ──► LIVE_DISABLED ──► LIVE_AUTHORIZED ──► LIVE_PAUSED
            ▲                    │                    │
            │                    │                    │
            └────────────────────┴────────────────────┘
                              (explicit operator action)
```

**Separation guarantees:**

1. **Connection ≠ Authorization:** `ProviderAdapter.connected == true` does NOT set `Project.execution_mode`. Authorization requires explicit operator action authenticated via `require_user` and writes a durable audit trail.

2. **UI ≠ Authority:** Frontend state is a pure cache of the backend response. No optimistic updates; button click disabled while mutation is in-flight; page re-fetches on success.

3. **RUNNING ≠ LIVE:** Project lifecycle machine is orthogonal to execution authority machine. A project may be RUNNING in PAPER mode indefinitely. Transitioning to LIVE_AUTHORIZED requires explicit `execution_mode` mutation separate from lifecycle mutation.

4. **Restart safety:** On application boot, `execution_mode` defaults to `LIVE_DISABLED`. No persisted LIVE_AUTHORIZED state is auto-restored. Operator must re-authorize after restart via explicit UI action.

5. **Kill-switch isolation:** Resetting `kill_switches.state` from TRIGGERED to ARMED does not change `Project.execution_mode`. Kill-switch governs engine-level order gating; execution authority governs project-level broker routing decision.

## 4. Migration & Backfill Analysis

### 4.1 Deterministic Mappings

| Current Representation | Project Field | Deterministic? |
|------------------------|---------------|----------------|
| `strategy_versions.strategy_id` | `Project.slug` | Yes — direct string match |
| `strategy_versions.display_name` | `Project.name` | Yes — direct string copy |
| `strategy_versions.config` | `Project.config` | Yes — JSON blob copy |
| `strategy_versions.version` | `Project.config_version` | No — version semantics differ ("strategy algorithm version" vs "project configuration snapshot") |
| `paper_accounts.is_active` | Project active flag | Partial — account toggle ≠ project lifecycle |
| `paper_accounts.name` | Project name heuristics | No — account naming is ad-hoc ("Test Account {uuid}") |

### 4.2 Ambiguous Mappings Requiring Assumptions

- **Project boundaries:** Current architecture has no explicit project identity; grouping strategies (e.g., "Daily XAU", "NIFTY F&O") is implied by naming conventions, not enforced by schema.
- **Execution mode backfill:** All newly created projects default to `PAPER`. Migration cannot infer historical LIVE intent.
- **State backfill:** Projects default to `STOPPED` with audit log entry `backfilled_from_strategy_version`.

### 4.3 Key Compatibility Risks

- Introduction of `Project` entity creates a new top-level FK target (`project_id`) that all downstream entities (orders, positions, signals) may eventually reference. Adding NOT NULL FKs to existing tables would be a breaking change requiring backfill of `project_id` on millions of rows.
- `strategy_id` string tag on `paper_orders` cannot be replaced with FK to `strategy_versions` without risking integrity errors on legacy free-form tags. Recommended approach: keep string tag and add optional `strategy_version_id` FK alongside it (dual-write period).
- Kill-switch global singleton conflicts with per-project kill switches — migration must preserve global override precedence.

### 4.4 Phased Foreign Key Rollout

1. Phase 1: Create `projects` and `project_strategy_assignments` with no FKs into legacy tables.
2. Phase 2: Add nullable `project_id` FK to `paper_orders`, `research_signals`, `research_reports`.
3. Phase 3: Backfill `project_id` via deterministic `strategy_id` → project slug mapping.
4. Phase 4: Enforce NOT NULL after backfill validation and audit log verification.

### 4.5 Affected APIs & Frontend Views

- **APIs:** `/api/v1/paper/orders`, `/api/v1/paper/positions`, `/api/v1/paper/summary`, `/api/v1/monitoring/strategies`, `/api/v1/research/*`.
- **Frontend:** Dashboard project cards, Orders stream (filter by project), Positions view, Reconciliation console, Risk Operations console.

### 4.6 Rollback Implications

- Project entity is additive. Rollback requires only dropping new tables and reverting optional FK columns; legacy data remains intact.
- Audit log entries created during backfill would be retained as historical record.

## 5. Research/Backtesting Relationship

### 5.1 Recommendation: Immutable Version References

**Historical backtest results MUST reference immutable StrategyVersion + Configuration snapshot, NOT the mutable Project or mutable Strategy.**

**Rationale:**
- Reproducibility requires frozen code and parameter sets. A Project's lifecycle status, execution mode, and risk limits change over time; freezing those into a backtest report would conflate operational state with research results.
- StrategyVersion already stores `config_sha256` and `config` JSON, forming an immutable fingerprint. Backtest reports should FK to `strategy_versions.id` (UUID) rather than the mutable `strategy_id` string.
- Project association is an optional metadata tag (`project_id` nullable on `research_reports`) for filtering and dashboard aggregation, not a primary key relationship.

### 5.2 Proposed Schema Additions

```python
class ResearchReport(Base):
    # Existing fields...
    strategy_version_id: Mapped[UUID] = mapped_column(ForeignKey("strategy_versions.id"))
    project_id: Mapped[UUID | None] = mapped_column(ForeignKey("projects.id"), nullable=True)
    
    # Immutable snapshot captured at report time
    config_snapshot: Mapped[dict] = mapped_column(JSON)
    config_sha256: Mapped[str] = mapped_column(String(64))
```

### 5.3 Reproducibility Approach

1. Backtest execution captures `strategy_version.id`, `strategy_version.config`, and `instrument_id` at runtime.
2. Report stores `config_snapshot` JSON and `config_sha256` fingerprint.
3. Future re-runs can verify fingerprint match before comparing metrics.
4. Project-scoped queries filter by `project_id` for aggregate views, but individual report reproducibility is independent of Project mutations.

## 6. Control Capability Roadmap

### 6.1 Dependency Matrix

| # | Capability | UI Dependency | API Dependency | Service Dependency | Schema Dependency | Audit Dependency | Testing Requirement |
|---|------------|---------------|----------------|-------------------|-------------------|------------------|---------------------|
| 1 | Project START/STOP | Dashboard card buttons | POST /projects/{id}/start, /stop | project_service | projects table, status enum | audit_logs | State machine transitions, auth |
| 2 | Project PAUSE/RESUME | Dashboard card buttons | POST /projects/{id}/pause, /resume | project_service | projects table | audit_logs | Transition validation |
| 3 | Strategy TEST | Strategy editor panel | POST /strategies/{id}/test | test_signal_engine | strategy_versions | audit_logs | Synthetic signal safety |
| 4 | PAPER account reset | Risk Ops console | POST /paper/accounts/{id}/reset | paper_account_service | paper_accounts | risk_events | Capital state reset |
| 5 | Risk-limit editing | Risk Ops console | PATCH /paper/accounts/{id}/limits | risk_service | paper_accounts | audit_logs | Validation, auth |
| 6 | Broker LIVE/PAUSED | Broker panel | POST /projects/{id}/execution-mode | broker_auth_service | projects.execution_mode | audit_logs | LIVE authorization flow |
| 7 | Order cancel/modify | Orders view | DELETE /paper/orders/{id}, PATCH | paper_trading_engine | paper_orders | risk_events | State machine (no cancel for FILLED) |
| 8 | Provider connect/disconnect | Broker panel | POST /providers/{id}/connect | provider_adapter | provider registry | audit_logs | Connection health |

### 6.2 Ordered Prerequisites

1. **Project entity + lifecycle machine** (prerequisite for 1, 2, 6).
2. **PAPER account reset** (independent; lowest risk; can proceed before Project).
3. **Risk-limit editing** (independent; requires audit infrastructure).
4. **Strategy TEST** (requires safe synthetic signal engine with no broker routing).
5. **Broker LIVE/PAUSED** (requires Project entity + explicit authorization workflow).
6. **Order cancellation/modification** (requires order state machine hardening).
7. **Provider connect/disconnect** (requires provider adapter health abstraction).

## 7. Impact Analysis & Coupling Risks

### 7.1 High-Impact Modules

| Module | Impact Level | Reason |
|--------|-------------|--------|
| `app/paper_trading/engine.py` | High | Direct dependency on order submission, risk validation, position MTM. Project coupling must avoid circular imports. |
| `app/paper_trading/models.py` | High | FK changes affect all paper trading tables. |
| `app/research/routes.py` | Medium | Adding project-scoped filters changes query parameters. |
| `apps/web/src/DashboardView.tsx` | Medium | Project cards currently show strategy/config stubs; Project entity changes data shape. |
| `apps/web/src/main.tsx` | Low | Navigation unchanged; only view component props change. |

### 7.2 Coupling Risks

- **God Object Risk:** A Project model that bundles strategies, accounts, brokers, and risk limits becomes a tightly coupled monolith. Mitigation: use junction tables (`ProjectStrategyAssignment`, `ProjectAccountAssignment`) and keep domain services separate.
- **Circular Dependencies:** Paper trading engine imports Project service; Project service imports paper trading engine for position queries. Avoid by extracting shared interfaces in `app/projects/interfaces.py`.
- **Global Kill Switch Conflict:** Per-project kill switches must not override the global safety halt. Enforce precedence: global KillSwitchState.TRIGGERED blocks all projects regardless of project state.

### 7.3 Recommended Service Boundaries

```
app/
  projects/
    models.py          # Project, ProjectStrategyAssignment
    service.py         # Lifecycle transitions, execution mode authorization
    routes.py          # REST endpoints
    interfaces.py      # Shared protocol for engine callbacks
  paper_trading/
    engine.py          # Order submission (unchanged; Project service calls into it via interface)
    routes.py
  research/
    routes.py          # Report queries with optional project_id filter
  brokers/
    adapter.py         # Provider connectivity abstraction (future)
    auth.py            # LIVE authorization workflow (future)
```

## 8. V2.6 Decision

**DECISION: B — PARTIALLY**

### Evidence

- **Can proceed independently:** Research reporting improvements (adding `config_snapshot`, `config_sha256`, immutable `strategy_version_id` FK) and PAPER account reset do not require the Project entity. They address backtest reproducibility and operational safety directly.
- **Must wait for Project schema:** Project START/STOP, PAUSE/RESUME, and LIVE/PAUSED authority require the Project entity and its state machine. Building UI for these capabilities before the backend state machine exists would produce decorative controls without enforcement.
- **Partial compatibility path exists:** The proposed phased FK rollout (nullable `project_id` on research tables) allows backtesting integration to land first, with Project backfill following without downtime.

### Recommended Immediate Next Implementation Phase

**V2.6 — Research + Backtesting Integration (Phase 1):**

1. Add `strategy_version_id` FK and `config_snapshot` / `config_sha256` to `research_reports`.
2. Add optional `project_id` nullable FK to `research_reports` and `research_signals` (schema-ready for future Project backfill).
3. Add PAPER account reset endpoint (`POST /api/v1/paper/accounts/{id}/reset`) with risk event audit.
4. Update Dashboard project cards to display strategy version fingerprints and backtest reproducibility indicators.
5. Do NOT implement Project entity, lifecycle controls, or LIVE execution in this phase.
